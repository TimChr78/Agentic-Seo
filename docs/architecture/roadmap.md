# Roadmap: implementation plan (wave 1)

> Status: plan (2026-11-12), not started. Team of one, assisted by agents. No dates.

**Ordering principle.** We inherit Agentic Marketing's rule: build first the foundations that are expensive to retrofit. These are the command registry with action classes, tenancy, artifacts, the policy hook, the provider gateway and the SSRF-safe fetcher.

**Revised after the external review (2026-11-12).** The first slice now delivers the product's distinguishing value end to end, but thin: audit → evidence-backed recommendation → GitHub pull request → deployment verification, all at L1, on the pilot site. Breadth comes afterwards: more checks, market data, tracking and AI visibility. Autonomy beyond L1 comes last, once outcome measurement has real results to stand on.

## Spikes (before Phase 0's design freeze; each answers one narrow question)

| # | Spike | Question it answers | Exit criterion |
|---|---|---|---|
| 1 | **Postgres under a mixed workload** | Does one Postgres keep the API responsive while a crawl, a GSC backfill and the job queue run at once? | A 50k-page synthetic site with a realistic link graph (≥ 30 pages/s on 2 vCPU, worker RSS < 512 MB), alongside a 16-month GSC backfill of 5M rows: API p95 < 300 ms, WAL and disk growth measured, `kill -9` mid-crawl resumes with no duplicates or lost discoveries |
| 2 | **Rendering egress** | Can the built-in Chromium renderer be forced through an SSRF-guarding proxy for every request type? | All payloads in the SSRF suite (subresources, WebSockets, redirects, DNS rebinding) are blocked; render fidelity and speed are recorded for 3 JS-heavy sites. Crawl4AI and Browserless are compared only on fidelity |
| 3 | **DataForSEO call lifecycle** | Real costs, timeout and `unknown` reconciliation, task-id recovery | Cost table for research, tracker and AI visibility actions; a forced timeout is reconciled without a double charge; estimate functions within ±10% |
| 4 | **GitHub connector for the pilot's framework** | Can a configured route→source mapping produce a correct patch, and can we detect "deployed" on the pilot's host? | On the pilot: `meta.title` and `schema.jsonld` patches open a PR; merge → deploy detected (Cloudflare Pages) → verified against the deployed commit; a stale-approval push sends it back to review; a revert PR works when files are unchanged and becomes a proposal when they have changed |
| 5 | **AI visibility sources** | DataForSEO LLM endpoints vs direct engine APIs with web search: agreement, cost, stability | Agreement matrix on 50 prompts; the default source chosen |

## The pilot

Like Agentic Marketing's MartechSignal pilot, wave 1 runs on a real site from Phase 1. MartechSignal is a static Cloudflare Pages site in a GitHub repository, which makes it ideal for the GitHub PR connector in Phase 1. **oresund.live** is the second pilot from Phase 1, also without a CMS. A self-hosted WordPress pilot joins in Phase 7 (open question 11).

## How we will build (process)

- **One phase per release line** (`0.1.x` = Phase 0–1, …), with a changelog fragment per PR (as `changelog.d/` in Agentic Marketing).
- **Issues per phase** with "done" criteria copied from this table; delegates (agents) take issues and humans review, following Agentic Marketing's `docs/process/delegates.md`.
- **Port, don't copy blindly.** Each ported package lands in its own PR with a provenance note (source commit) and with marketing-specific code removed (consent, profiles, journeys).
- **Every command ships with:** a zod schema, an action class, an MCP description written for LLMs, a test at the command layer, and docs.
- **Every screen ships with:** a visual baseline, axe in both themes, and the loading/empty/error states from the design contract.
