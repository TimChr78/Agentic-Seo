- Seed a site's change sets with the GitHub connector: `connectors.github.connect` stores a fine-grained token (sealed, never returned) plus the route-to-source mapping, the base branch and the deploy detector, and `connectors.github.status` explains what it is configured to do.
- Draft change sets with `changes.create`: each change is resolved through the mapping, applied in memory and stored with its base commit, source hash and diff, so a route the mapping cannot reach is refused before anyone reviews it.
- Submit a change set with `changes.requestApply`: the impact engine judges it by its strongest change and the traffic at risk over every affected URL, an unverified site is refused, more than 20 redirects always needs a person, and a second change set that touches the same URL or file is held with the first one named.
- Approved change sets become one pull request each (`changes_apply`), with the per-URL before/after, the verification plan and the rollback plan in the body; a retried job adopts only a branch or pull request whose commit is exactly the reviewed change (same parent and tree), and withdraws the approval when it is not.
- `changes_poll` follows the pull request every five minutes: a commit pushed after approval sends the change set back to review and closes the pull request, a merge with unapproved commits fails the change set before any deploy, a merge starts deploy detection, and a deploy that never appears (pending or undetectable) is reported as not detected after the configured window.
- Verification re-fetches the affected URLs after the deploy is detected and records pass, fail or unknown per change against the deployed commit; a redirect's path is resolved against the site origin and its status and `Location` are checked, and a page that cannot be fetched is retried three times before it counts as a failed verification.
- `changes.rollback` proposes a draft rollback change set (linked as `rollback_of`) with the original's action class and reach; it writes nothing to GitHub, its pull request opens only after approval, and the original becomes rolled back only when the rollback is verified.
- Change-set content is server-owned: the generic artifact commands refuse it, `config.import` refuses it on every write path (a new artifact and an existing one), and approval and the apply worker re-derive each path, hash and diff from the repository before anything reaches a branch.
- The apply worker adopts a branch or pull request from an earlier attempt only when its commit's tree matches the base tree entry for entry (path, type, mode and blob SHA) with the reviewed blobs at their base modes; an executable bit, a symlink, a submodule, an extra file or a deleted file is refused.
- `changes.rollback` proposes a draft rollback change set (linked as `rollback_of`) judged with the original's action class and reach; a change it cannot invert is listed in `uncoveredChanges` with the reason, such a proposal is never exact and never marks the original rolled back, and rejecting the proposal closes its run so another can be requested.
- One rollback proposal per original at a time: the command locks the original run row and 0010 adds a partial unique index, so two simultaneous requests give one proposal and one clear refusal.
- The apply and verification jobs are queued in the transaction that makes them due, and the poller re-queues an `approved` or `deployed` change set whose job was lost.
- The site setup checklist's site connector fact now follows the GitHub connection.
