- Seed a site's change sets with the GitHub connector: `connectors.github.connect` stores a fine-grained token (sealed, never returned) plus the route-to-source mapping, the base branch and the deploy detector, and `connectors.github.status` explains what it is configured to do.
- Draft change sets with `changes.create`: each change is resolved through the mapping, applied in memory and stored with its base commit, source hash and diff, so a route the mapping cannot reach is refused before anyone reviews it.
- Submit a change set with `changes.requestApply`: the impact engine judges it by its strongest change and the traffic at risk over every affected URL, an unverified site is refused, more than 20 redirects always needs a person, and a second change set that touches the same URL or file is held with the first one named.
- Approved change sets become one pull request each (`changes_apply`), with the per-URL before/after, the verification plan and the rollback plan in the body; a retried job adopts the pull request it already opened instead of opening a second.
- `changes_poll` follows the pull request every five minutes: a commit pushed after approval sends the change set back to review and closes the pull request, a merge starts deploy detection, and a deploy that never appears is reported as not detected after the configured window.
- Verification re-fetches the affected URLs after the deploy is detected and records pass, fail or unknown per change against the deployed commit; a page that cannot be fetched is retried three times before it counts as a failed verification.
- `changes.rollback` opens an exact revert pull request while every touched file still matches the merge, and otherwise proposes a draft change set with the inverse edits and says which files moved.
- The site setup checklist's site connector fact now follows the GitHub connection.
